# Ocura OSS 0.7 ideas draft

Status: Local 0.7 planning draft, updated 2026-10-27. Naming migration and the
usability priorities below are selected for 0.7. They are planned work, not
released behavior. The naming layer, opt-in structured errors, and fresh-caller
history example are implemented in the 0.7.0.dev0 development checkout; release
qualification and publication are separate. Other ideas remain candidates, with no chosen annotation
format, final new command syntax, or release date.

The [2026-10-28 follow-up draft](0.7-followups.md) turns the remaining release
decisions and candidate ideas into bounded proposals with acceptance criteria.
It identifies what is already implemented and keeps exploratory additions separate
from the selected 0.7 scope. The foundation discussion below is historical context.

Make existing experiment evidence easy for an agent or script to find, read,
reference, and move between workflows. The caller builds the report and interprets
the result. Ocura supplies accessible records and evidence.

Keep the standard-library-only runtime, ordinary local files, and functional CLI
and Python interfaces. New access paths should also help people using the terminal.

## Agreed naming and usability priorities

### Naming migration

Use these canonical public primitive names in 0.7:

| Existing name | Canonical name | Responsibility |
| --- | --- | --- |
| `Den` | `Ledger` | Identity of the project-local ledger and its default pathway |
| `Pathway` | `Pathway` | A line of work containing declared parameters and potentially several runs |
| `Atom` | `RunRecord` | The finalized record of a command attempt and its evidence, including failed or abandoned attempts |
| `Chokepoint` | `BranchPoint` | A terminal evidence boundary that may serve as a branch source |

Lead documentation, examples, help, and new public interfaces with the canonical
names. Keep the distinction between the existing unfinished `Attempt` journal and
a finalized `RunRecord`. A `BranchPoint` is not a workspace or model checkpoint;
branching creates lineage metadata and does not restore or execute a workload.

#### Compatibility in 0.7

- Inventory old imports, types, methods, keyword arguments, returned attributes,
  CLI spellings, JSON fields, and error terminology. Keep existing callers working through deliberate
  aliases or adapters, including `Initialization.den` and
  `RunExecution.atom` / `RunExecution.chokepoint`. Publish one migration table
  showing the canonical replacement for each affected public name. If both old
  and new keyword spellings are accepted, reject conflicting values explicitly.
- Preserve established CLI JSON and Python serialization contracts. Specify an
  explicit transition for renamed output fields before changing them; do not
  silently replace keys or add duplicate representations throughout responses.
- Preserve existing schema-2 ledger records, field names, record kinds, directory
  names, typed ID prefixes, log bytes, checksums, and retained manifests. Canonical
  interfaces accept the existing IDs without rewriting them. Reading an existing
  ledger must not migrate it as a side effect.
- For this naming migration, new records also retain the schema-2 storage names.
  Public naming and stored naming are separate contracts. Renamed or removed
  stored fields require a future schema version under the existing
  [format compatibility rules](../state-and-verification.md#format-compatibility).
  Older schema-1 ledgers retain their existing separate migration path.
- Keep storage-capability decisions, including gzip compatibility, separate from
  the naming migration; unchanged terminology does not settle those decisions.

#### Later retirement of compatibility names

Treat old public names as transitional compatibility, with canonical names used
for new work. They can be phased out in a later explicitly announced breaking
release after documenting replacements, a deprecation period, and downstream
migration checks. Choose removal versions deliberately; 0.7 does not promise a
specific removal date. Deprecation diagnostics must preserve machine-readable
output contracts.

Removing an old API alias does not require dropping support for stored ledgers.
Retire an old storage format only through a separate versioned migration plan
with a documented support window and a verified conversion path. Preserve the
original evidence; if a future format changes identities or manifests, provide
an explicit mapping and migration receipt rather than silently replacing them.

#### Migration acceptance

- Existing Python and CLI workflow examples continue to work, and canonical-name
  examples produce equivalent execution, failure, recovery, branching, comparison,
  and verification results.
- Existing schema-2 fixtures and retained manifests verify without changed record
  or log bytes. Canonical interfaces can read and extend those ledgers using the
  existing stable identities.
- Compatibility checks cover result attributes, keyword arguments, serialized
  output, and ID resolution as well as imports and command names.
- The fresh-caller history example below uses canonical vocabulary and explains
  legacy names only where needed to interpret an existing interface or record.

### Structured errors and retry guidance

Give JSON callers stable error categories and useful context without requiring
them to parse English diagnostics. Preserve known record identities when an
operation fails. Recorded workload failures remain results with their actual
outcomes, rather than becoming interface errors.

Handle uncertain retries in the same design. An error or missing response does
not establish that a command never ran. Distinguish failure before execution,
recorded execution, and uncertain execution when the available evidence permits
it. Explain how to inspect attempts and history before retrying and when recovery
can close an abandoned attempt. Do not imply automatic deduplication or exactly-once
execution. The development contract is documented in the
[CLI error reference](../cli.md#structured-errors-unreleased) and must be qualified
with the compatibility checks before release.

### Complete history workflow

Provide an executable example in which a fresh caller receives only a ledger
root and reconstructs a baseline, its variations, and every relevant attempt.
Include a failed attempt followed by a successful retry, unfinished work, and a
variation with no execution evidence. Make the comparison's selected latest run
distinct from the complete history, and explain paging completeness while runs
are active. Retrieve verified evidence through documented interfaces and cite
what supports the interpretation without constructing private storage paths.

### Clear terminology and fewer handoffs

Explain the user's workflow in familiar language before introducing record types.
Use `Ledger`, `Pathway`, `RunRecord`, and `BranchPoint` consistently, following the
naming migration above. A pathway can contain several runs, and creating a
variation does not execute a command. A terminal
branch source does not restore workspace files, process state, or model weights.
Explore fewer ID handoffs while keeping the selected source explicit.

Package restraint should prevent unnecessary dependencies, bundled files, and
implementation complexity. Keep size checks as development guardrails; user
documentation should explain capabilities and workflows without promoting package
byte counts, module counts, or source-line totals.

Other ideas below remain candidates; agreeing on these priorities does not add
all of them to the release scope.

## Released 0.6.0 foundation

The [current workflow](../automation.md) already provides JSON output, typed Python
results, explicit branch reasons, parameter deltas, captured logs, and verification.
Agents can retain full IDs and read verified output without scraping terminal text.

Some useful pieces are harder to discover or compose:

- The CLI lists pathways and terminal chokepoints, while `attempts` lists only
  unfinished executions. There is no dedicated listing of all finalized runs.
- `compare` selects the newest run on each child pathway. Earlier attempts remain
  stored, but a caller must collect them separately.
- Branch reasons describe a variation. There is no general annotation interface
  for a particular run or a location within its evidence.
- The [migration tool](../../tools/migrations/README.md) converts old Ocura ledgers;
  it does not import arbitrary existing logfiles.
- The [compression draft](../autocompression.md) reads raw and gzip storage through
  the same interface. Its content reader still buffers a whole decoded stream,
  and reading currently needs writable lock storage inside the ledger.

## Ideas board

| Area | Candidate direction | Benefit | Question to settle |
| --- | --- | --- | --- |
| Agent access | List finalized runs and inspect related evidence with bounded JSON responses | Fewer file walks and tool calls to assemble an experiment history | Which small set of selectors covers real caller needs? |
| Notes and references | Attach context to records or exact evidence locations | Preserve useful observations where a later caller can find them | What belongs in a note, a tag, or a reference? |
| Conversion | Import existing logs and export selected evidence | Adopt Ocura gradually and reuse evidence in other tools | Which facts are available, and which must stay unknown? |
| Shorter workflows | Reduce ID handoffs in common operations | Less terminal work and simpler agent instructions | Which shortcuts preserve explicit source selection? |
| Archives and compression | Read large, compressed, and read-only evidence predictably | Keep long histories usable with modest resources | How should bounded reads preserve verification before output? |

## Agent access

Start with retrieval questions rather than report templates:

1. Which runs belong to this baseline or pathway, including earlier failures?
2. What are this run's outcome, reason, declared inputs, and evidence references?
3. Which notes or references apply to this record or log location?
4. How can the caller retrieve the relevant bytes and cite exactly what it used?

A candidate access layer would offer a finalized-run listing and a focused record
inspection operation. Inspection could return the selected record, its immediate
relationships, annotation references, and log metadata together. Log contents would
remain an explicit read, keeping routine JSON responses small.
Keep command arguments an explicit request too, following current summary defaults.

Keep selectors narrow initially: record ID, pathway or source, outcome, and a
bounded number of entries. Add tag filtering if tags prove useful. Use a defined
ordering and continuation behavior so callers can retrieve a complete history
while other runs are being added. Avoid silently dropping earlier failures or
returning a partial history as though it were complete.

State verification scope in machine-readable output. Reading record metadata,
checking one selected stream, and verifying a whole ledger are different actions.
A metadata listing must not claim that its referenced log bytes were checked.
Existing verification guarantees should retain their meaning.

The agent should be able to assemble its own account of an experiment using these
primitives. Metric extraction, conclusions, and report presentation stay with the
caller. The [autoregressive example](../../examples/autoregressive/README.md#read-the-saved-result)
already demonstrates that separation.

## Notes tags and references

These serve different purposes:

- A **note** adds context, such as an observation, caveat, or interpretation.
- A **tag** helps retrieve records, such as `baseline`, `overflow`, or `follow-up`.
- A **reference** points to evidence or context elsewhere, optionally at a precise
  location.

An attached note or tag is an assertion by its writer. It does not change a run's
recorded outcome or establish that an interpretation is correct.

### Scenarios to explore

- Attach an observation to a failed run: "First attempt with the larger batch."
- Mark a region of stderr: "The overflow starts here."
- Point from a variation to a code location, configuration, issue, paper, or another
  tracker run that explains the change.
- Mark a location in a small JSON output, so an agent can revisit the reported
  validation loss without guessing which occurrence was intended.
- Group relevant records for later retrieval without changing their parameters.

### Possible forms

| Form | Shape | Advantage | Cost or limitation |
| --- | --- | --- | --- |
| Attached notes with optional references | A target plus text, with optional locations | Small initial surface; naturally supports context beside evidence | Retrieval labels would still need a decision |
| Separate notes tags and references | Three explicit operations with their own fields | Each has clear retrieval and validation rules | More commands, record types, and concepts |
| External notes with stable Ocura references | Markdown or another caller-owned document points into the ledger | Preserves existing note-taking habits | Ocura cannot automatically discover those external observations |

The leading experiment is attached notes with optional references. Try it against
the scenarios before choosing storage or syntax. Tags can be added if repeated
retrieval needs justify them. External documents should remain usable regardless
of whether Ocura stores notes itself.

### Reference locations

Explore a few explicit targets rather than an arbitrary locator language:

| Target | Candidate location | Important behavior |
| --- | --- | --- |
| Ocura record | Full typed record ID | Stable when storage representation changes |
| Captured log | Run ID, stream, original digest, and optional byte range | Addresses original decoded bytes, independent of a `.gz` path |
| Text within a log | Optional line range and declared decoding | Convenient for people; define newline and encoding behavior |
| Structured result | Optional JSON Pointer within identified evidence | Caller selects the value; Ocura need not interpret it as a metric |
| Project file | Relative path, optional revision and content digest | Distinguish locating a file from retaining a copy of it |
| External context | URL or external system ID | Store the reference without automatically fetching it |

Byte positions are a promising canonical anchor for logs; line ranges are a
possible convenience. A digest mismatch should identify a stale reference rather
than silently selecting the same positions in different content. Returning a
snippet should include its source and verification scope so a caller can cite it.

Open decisions include target scope, multiple labels, note revisions or corrections,
and how notes participate in verification and manifests. Separate annotation
records are worth evaluating because they could preserve finalized execution
records. Their storage and compatibility behavior still need design.

## Converting existing evidence

### Importing logfiles

Support the person who already has a useful `run.log` and wants to keep working
from it. A first importer could accept one explicitly selected file plus optional
context, preview the resulting record, and copy the bytes into owned ledger storage.
It must never execute a command found in that file or supplied as historical context.

Preserve the distinction between an imported file and an execution Ocura observed.
The current atom model requires execution facts such as an outcome and start time.
An arbitrary log cannot reliably supply those facts. Do not fill gaps with a
passing outcome, file modification time, or an invented command.

Consider an imported-evidence record that can be referenced from later work, or a
deliberately limited attachment facility. Decide separately whether imported
evidence can serve as a branch source. Byte verification establishes what was
imported; user-supplied historical metadata remains a declaration.

Useful import behavior to explore:

- Retain original bytes, digest, import time, and supplied source context.
- Make copy versus external reference explicit; copying is the simpler initial
  way to avoid later loss when the original file moves.
- Leave missing execution facts unknown and make that visible to callers.
- Preserve originals and identify repeated imports or partial attempts in a receipt.
- Begin with plain files. Existing gzip input can follow once original-byte
  identity, decoding limits, and storage capability rules are settled.

Directory guessing, automatic log parsing, and bulk reconstruction of experiment
lineage can wait for concrete examples that justify them.

### Exporting to other workflows

Existing JSON output is the starting point. Explore a selected-evidence export:
records and relationships, annotations, source identities, and an explicit choice
of whether to include log bytes. Preserve failed and incomplete evidence and state
what the selection excludes.

Distinguish a portable archive that Ocura can read again from a projection into
another tool's format. A projection may omit fields or relationships; its receipt
should describe that mapping. Native round trips should retain original evidence
identities and bytes.

Define which related records a portable selection must include and how excluded
references are represented. Existing IDs with different content must cause a
conflict, rather than an overwrite or a silent change of identity.

Keep destination-specific conversions in small external adapters initially. An
MLflow adapter, for example, could use that environment's MLflow installation;
the core package would continue to emit ordinary data without importing its SDK.
No automatic uploads are needed for the first export path.

## Shortening commands and flow

Existing short ID prefixes already help people typing commands. Agents should
continue to retain full IDs, which remain stable as more records are added.

Explore two simplifications:

1. Let a caller start a variation from an explicit source with a reason and command
   in one operation. Reuse branch creation and recording rather than implementing
   a second execution path.
2. Make related records and evidence discoverable from one selected ID, reducing
   the need to alternate between listings and direct JSON file reads.

Any combined operation needs clear partial-failure behavior. If the variation is
created but execution cannot start, return its identity and actual state. Keep
command token boundaries, parameter substitution, and recorded failures consistent
with the existing runner.

Prefer fewer required handoffs over many spelling aliases. Friendly names and
saved selectors are additional possibilities, but would introduce ambiguity and
concurrency rules. Do not make a write depend on an implicit "latest run" that can
change between agent calls.

## Archive reading and compression

Keep one logical read interface for raw and compressed evidence. Notes and
references should use original content identities, not physical backing paths.
Normal reading should not require a persistent decompression conversion.

### Bounded reads

A small requested snippet should not require memory proportional to the entire
decoded log. However, full SHA-256 verification of a gzip stream still requires
reading the full original stream; a small response does not imply a cheap seek.

| Approach to evaluate | Resource cost | Verification behavior |
| --- | --- | --- |
| Decode into temporary storage, then read the requested content | Bounded RAM, temporary disk space, one decode | Can verify before releasing content; scratch space must work outside a read-only archive |
| Verify first, then decode again for output | Bounded RAM, two decoding passes | Requires a stable source across both passes |
| Stream directly and verify at completion | Bounded RAM and early output | Earlier bytes escape before a final mismatch is known; needs an explicit different contract |

Preserve the existing bytes-returning API for small outputs. Explore a separate
file-like or context-managed access path for large outputs before choosing a CLI
option. Strict verification before output remains the starting contract.

Chunk checksums or seek indexes could improve repeated access, but add a new
format and integrity model. Measure ordinary gzip access before adopting them.

### Read-only archives

An archive should be inspectable without creating lock files inside it. Evaluate
external lock coordination or an explicit mode for stable archived storage.
Simply skipping locks on a ledger with active writers would weaken consistency.

Make verification and reference resolution work after the archive is moved, using
ledger-relative identities. External file references may become unavailable;
report that separately from corruption of retained evidence.

### Compression policy and compatibility

Use the current draft as a starting experiment: one pass over the completed run's
eligible logs, with minimum size and savings thresholds. Settle automatic versus
opt-in compression, read-only behavior, and the smallest useful control surface.

Declare storage capabilities so an unsupported reader can explain what it cannot
read. An unchanged JSON schema alone does not establish compatibility with gzip
backing. Keep a verified route back to raw storage where downgrade support is
promised.

Measure metadata discovery separately from content verification. Use small logs,
large repetitive logs, poorly compressible logs, binary output, and many runs.
Record latency, peak RAM, temporary disk use, and bytes read. Avoid rescanning or
decoding every log merely to list matching records or notes.

## Order of exploration

Implement the agreed naming migration alongside structured errors and retry
guidance, the complete history workflow, and clearer terminology. Settle the
public compatibility map before updating examples and error fields. The candidate
areas below do not become release requirements merely by appearing in this plan.

1. **Agent retrieval:** exercise a history with a baseline, multiple variations,
   and a failed retry. Identify the minimum missing read operations and selectors.
2. **Archive access:** evaluate bounded readers and read-only storage against the
   current compression prototype. This can proceed independently of annotation form.
3. **Annotation sketches:** try the same note and reference scenarios with each
   candidate form. Check retrieval and citation needs before fixing a record format.
4. **Import and export:** use a real existing logfile and a selected Ocura history
   to settle provenance, missing facts, and portable identities.
5. **Workflow shortcuts:** shorten the resulting common path without adding
   overlapping ways to run commands or select a source.

Before implementation, turn selected ideas into focused proposals under the
[contribution guidance](../../CONTRIBUTING.md#before-you-start), including any new
command, record, or compatibility surface. The current implementation is identified as a development version; candidate
ideas do not imply additional release commitments.

## Checks for a useful 0.7 scope

- Canonical primitive names are consistent across the selected workflows; old
  public callers and existing schema-2 ledgers satisfy the migration acceptance
  checks above, with a documented route toward later alias retirement.
- An agent can retrieve every relevant attempt, reason, and evidence reference
  through documented interfaces without constructing private storage paths.
- Notes and locations survive compression and a native export/import round trip,
  or clearly explain which reference could not be retained.
- An existing logfile becomes accessible without a fabricated execution history.
- Large-log access has bounded memory under the selected contract, and a read-only
  archive can be inspected without changing it.
- Selected content is verified according to an explicit scope. Missing, stale,
  imported, and unverified evidence remain distinguishable.
- Common terminal and agent workflows require fewer handoffs while retaining
  explicit source selection and the existing failure behavior.
- The core retains zero runtime dependencies and delegates report composition,
  workload interpretation, and external service integrations to its callers.
