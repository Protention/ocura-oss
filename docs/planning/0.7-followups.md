## What is already implemented

The current checkout is `0.7.0.dev0`, not a published release. It includes:

- Canonical `Ledger`, `Pathway`, `RunRecord`, and `BranchPoint` vocabulary with
  legacy public interfaces and schema-2 storage retained.
- `runs` and `show`, including failed retries, explicit verification scopes, and
  a documented completeness rule for paging while writers are active.
- Opt-in `--json-errors`, known execution identities, execution-state diagnostics,
  and guidance to inspect uncertain results before considering another run.
- Bounded verified log access, raw/gzip reading, and stable archive mode.
- A fresh-caller history example using public readers, preserving empty
  variations and unfinished attempts, producing precise evidence references,
  and retaining structured diagnostics alongside existing error text.
- Explicit-source `run --from ID --reason TEXT` and corresponding Python keywords,
  composing branch creation and execution while preserving two-step callers.

`compare` deliberately selects one latest run per child pathway; full history
comes from discovery. Archive mode does not freeze an active ledger. Exact snapshot
cursors remain optional unless a stronger live-completeness promise is selected.

## Q2. Resolve the inherited compression release policy

**Problem:** Compression is implemented, but physical gzip storage affects older
readers despite unchanged schema-2 records. The draft policy is not a naming issue.

**Decision (2026-10-30):** Logs stay raw by default. `run --compress` or
`--compress-min-bytes N` opts a run in, and `compress`/`decompress` convert
existing logs. Raw logs stay readable by 0.6 and by standard tools at their
recorded paths, and compression adds time before `run` returns: on one Windows
machine, +3.7 s for a 155 MB text log stored as 16.6 MB, and +16 s for a 192 MB
base64 log stored as 145 MB. Run from v0.6.0 source, a compressed ledger fails
`verify` (missing log, orphaned `.gz`) and refuses to branch from or compare those
runs; after 0.7 `decompress`, 0.6 `verify` passes. Repeat that with an installed
0.6.0 wheel during Q1.

**Scope:** Decide whether automatic compression ships in 0.7 and document its
upgrade/downgrade path. Explicitly accept or revise the documented ordinary-read
fallback when lock storage is unwritable. Review capability diagnostics separately;
do not add retention deletion, quotas, or a storage engine.

**Dependencies:** Existing raw/gzip readers, conversion controls, manifest checks,
archive behavior, and the final compatibility evidence from Q1.

**Acceptance:**

- Record the default and rationale. Conversion and downgrade preserve record
  bytes, IDs, original log bytes, checksums, and retained manifests. After
  decompression, exercise the promised path with an actually installed older
  reader. A new capability declaration cannot make an old reader gzip-aware;
  proposing one requires its own format/compatibility decision.
- Qualify the resource envelope for large raw/gzip logs and many runs: bounded
  excerpts still require full-stream verification, and paging repeats metadata
  scans. Record measured memory, temporary-storage, and latency behavior.
- Confirm archive reads require a stable copy and ordinary permission-denied
  read fallback has its documented scope; neither establishes a live snapshot.
- Verify denied locks cannot fall back to mutation for both `PermissionError`
  and `EROFS`, with both compression and decompression, including after a cached
  unlocked read. The guard is already implemented; retain it as a regression gate.

## Q3. Exercise return-to-existing-work usability

**Progress:** A fresh-context agent completed the synthetic conversion-history
exercise and exposed the intermediate pathway-ID handoff. See the
[walkthrough findings](0.7-usability-walkthrough.md). This covers one agent and a
command workflow beyond training; a human and an unfamiliar real history remain.

**Problem:** The example proves mechanics, not how easily a fresh caller can
understand an unfamiliar real history.

**Scope:** One human and one fresh-context agent inspect an existing authorized
history with a failed retry and empty variation. A second command-based workflow,
such as patch testing or data conversion, can test generality beyond the training
demo. Do not run expensive workloads or create a leaderboard for this exercise.

**Dependencies:** An installed candidate, current guides, and retained histories
whose authors can explain the intended relationships.

**Acceptance:** Given only the root, callers can locate and explicitly select the
baseline, account for all relevant attempts, identify missing/unfinished evidence,
and cite verified output without private storage paths. Record extra commands,
misunderstandings, and corrections. Keep uncertain live observations distinct from
complete settled history. Use this evidence to prioritize P1-P4, not to claim adoption.

## P1. Reusable references and attached observations

**Problem:** The example already emits precise log references, but there is no
general attachment interface for an observation on a run or location in evidence.

**Proposed first slice:** Review references using ledger ID, run ID, stream,
original digest, and optional range. Try attached text notes stored separately
from execution records; compare caller-owned Markdown before choosing a format.

**Non-goals:** Metric interpretation, scored conclusions, a full tag system,
arbitrary locator languages, fetching URLs, or rewriting run outcomes.

**Dependencies:** Current verified readers and example references. Decide target
types, note corrections, manifest participation, and reader/schema compatibility
before storing annotations in ledgers. Export can support notes only once these
identities and relationships are defined.

**Acceptance:**

- An observation on a failed run and a selected stderr region is discoverable
  through a documented interface without altering execution records.
- References resolve to the same original content after compression and moving a
  stable ledger copy; changed content produces a stale-reference error.
- Note text remains a writer assertion. Outputs distinguish checking the note,
  its target metadata, a selected stream, and the whole ledger.
- Corrections have explicit behavior, and old readers encounter a documented
  compatibility boundary. URL references are stored without network requests.

## P2. Portable selected-evidence export

**Problem:** Stable archive mode reads an already prepared copy; it does not select
and package a baseline's evidence for another workflow.

**Proposed first slice:** Preview and export a selected settled history to a new
destination with the required lineage closure, a selection receipt, and an
explicit choice about log inclusion. Define empty variations and excluded
relationships. An export without required logs is a projection, not a fully
verifiable native ledger.

**Non-goals:** Live snapshots, synchronization, automatic uploads, destination SDK
dependencies, destructive pruning, or importing arbitrary external logs.

**Dependencies:** Stable source policy, identity/conflict rules, and manifest
semantics. P1 is required only if the first export promises annotation support.

**Acceptance:** A moved native export can be read in archive mode and verified;
original execution identities, retained evidence, and failed attempts survive;
the receipt states the selection and exclusions. Conflicting IDs never overwrite
different content. Interrupted export leaves the source unchanged and the new
destination visibly incomplete rather than reporting success.

## P3. Import one existing logfile honestly

**Problem:** A logfile can be useful evidence without the execution facts required
for a `RunRecord`.

**Proposed first slice:** Preview copying one file into owned evidence storage
with its digest, import time, and declared source context. Use a separate
imported-evidence/attachment model rather than inventing an observed execution.

**Non-goals:** Inferring success, start time, command, or lineage from content or
file timestamps; executing historical commands; directory crawling; automatic
metric parsing; making imported evidence branchable by default.

**Dependencies:** Provenance, reader/schema, and reference proposals. Coordinate
with P2 for portability; importing external evidence differs from native restore.

**Acceptance:** Unknown facts stay unknown; declarations remain distinguished from
observed facts; original content is retained and verified; repeat imports and
partial failures produce clear receipts without replacing the source. Moving or
deleting the original file does not lose a copied attachment.

## P4. Reduce variation handoffs

**Problem:** One variation required creating a pathway and handing its ID to a run.
The Q3 synthetic walkthrough observed that transfer directly.

**Implemented slice:** `run --from ID --reason TEXT -- COMMAND`, or Python
`run(..., source_branch_point_id=ID, reason=TEXT)`, delegates to verified branching
and the existing runner. It removes the intermediate pathway-ID transfer while
keeping explicit source selection, existing results, and the two-step workflow.

**Non-goals:** Implicit latest-source writes, a second execution implementation,
scheduling, automatic retries, or exactly-once execution guarantees.

**Dependencies:** Branch validation, parameters, structured errors, and execution
provenance. Import/export is not a dependency.

**Acceptance:** Require the source, reason, and actual command; keep token
boundaries and parameter behavior equivalent to the existing two-step workflow.
If the pathway exists but execution fails or is uncertain, return its identity
and truthful execution state so inspection can precede any new run.

## P5. Retire legacy public names deliberately

**Problem:** Compatibility aliases are useful now but require a future support
policy. The naming migration already exists; this is not a second rename.

**Scope:** Inventory downstream use and propose a separately announced breaking
API release with replacement guidance and a deprecation period. Choose a version
only after checking maintained callers. Do not remove aliases in this 0.7 work.

**Dependencies:** The current naming map and compatibility tests, real downstream
call sites, and a decision about diagnostics that preserve JSON/error contracts.

**Acceptance:** Every removed import, keyword, property, method, or CLI spelling
has a documented replacement and migration check. Constructor/serialization
contracts are evaluated explicitly. API alias retirement does not silently
change stored kinds, directories, prefixes, manifests, or JSON keys; any such
change needs a separate versioned format/serialization transition.
