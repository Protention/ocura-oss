# Returning to an existing history: 0.7 usability exercise

On 2026-10-28, one fresh-context agent inspected a synthetic data-conversion
history using the installed candidate built from `47cb773`, public documentation,
and the corrected repository history example. It received the project root and
task, without fixture setup or expected answers. This is a bounded engineering
exercise, not a human study, adoption evidence, or a general quality benchmark.

The history contained a baseline, a failed trim attempt followed by a successful
retry on the same pathway, an independent case-folding variation, an unrun
normalization variation, and an unfinished attempt. Finalized logs included raw
and gzip storage. The caller reconstructed all these relationships, selected the
baseline explicitly, cited bounded verified output, and created and ran exactly
one new normalization variation. It did not recover or resubmit existing work.

Custodian checks confirmed that every pre-existing file was unchanged, the old
unrun variation and unfinished attempt remained, and exactly one pathway and run
were added. Verification against the retained manifest reported only the known
unfinished attempt. The synthetic command completed successfully.

## What the exercise exposed

| Observation | Response |
| --- | --- |
| Creating a variation required copying `branch.id` into `run --pathway`. | Add explicit-source `run --from ID --reason TEXT`, delegating to existing branch and run operations. |
| Baseline run labels were not inherited as pathway labels. | Keep the existing inheritance rule and explain it at the shortcut; repeat run-only labels deliberately. |
| History uses canonical names while CLI JSON preserves legacy keys. | Preserve compatibility and document the mapping; do not silently rename result keys. |
| `compare` selected the latest child attempt and omitted an earlier failure. | Keep history discovery first when reconstructing all attempts; comparison remains a summary. |
| Archive reading refused the unfinished history. | Keep the refusal, structured diagnostics, and stable-copy requirement. No recovery action is automatic. |

The caller made no wrong-source selection or erroneous workload retry. Its
18 workflow commands included documentation reads and deliberate cross-checks;
that total is not a minimum-command benchmark. The concrete simplification is
two mutation calls and one intermediate pathway-ID transfer becoming one call:

```console
ocura-oss run --from BASELINE_BRANCH_POINT --reason "combine normalization steps" --param mode=normalize --param input=synthetic-four -- python check_records.py --mode normalize
```

Source selection remains explicit. `--param` sets the new pathway's overrides,
and its run inherits them. Ordinary `run --pathway` still adds per-run labels.
The two-step workflow remains useful for planning an unrun variation or inspecting
it before execution.

A follow-up with the same caller used an installed wheel containing the shortcut
on a fresh copy of the original history. It completed the variation in one call,
with no intermediate pathway-ID transfer, and retained all original evidence.
The caller explicitly repeated the source run's input label. A separate archive
read verified all eight settled streams without changing or adding files. This
follow-up benefited from the caller's earlier familiarity; it is not an independent
blind comparison. Final review additionally fixed combined-call handling of
non-dictionary mappings and tested malformed parameter containers before mutation.

## Failure and compatibility boundaries

The history example keeps its `error` text and adds structured `error_details`
for fatal and individual stream failures. Existing success fields and exit
statuses remain unchanged. Missing or corrupted evidence is not hidden.

The combined operation does not provide transactional rollback or exactly-once
execution. Selection errors are rejected before creating a child. Later runner
validation or storage failure can leave a child, whose ID is retained alongside
the source and any known execution identities. Inspect uncertain execution before
another call; use the retained pathway explicitly when continuation is intended.
Repeating `run --from` creates another variation.

Regression coverage exercises old two-step callers, unchanged run JSON and exit
statuses, source verification, parameter inheritance, command-token boundaries,
partial failures and continuation, and appending to the frozen 0.5 ledger without
rewriting its existing files. Existing installed and shell CI gates cover both
interfaces. A human walkthrough and an unfamiliar real project remain open Q3
work; this exercise does not complete those gates.
